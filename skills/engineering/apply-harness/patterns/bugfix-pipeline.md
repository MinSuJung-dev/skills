# 버그 수정 파이프라인

## 구조: 순차 진행 (진단 → 조사 → 수정 → 검증)

## Phase 0: 버그 유형 분류 (수정 전 필수)

수정하기 전에 유형을 먼저 분류한다. 유형마다 접근법이 다르다.

### 임계값/민감도 버그
- "가끔 발생", "특정 조건에서만" 해당
- 임계값/필터/스코어링 로직 관련
- **원칙:** 수정 전 디버그 출력 강화 → 사용자와 협업해 점진 조정
- 임계값은 `static const`로 추출, 주석에 의미 기록

### 외부 SDK 좌표계/동작 버그
- ML Kit, Camera, 네이티브 SDK 등 예측 불가 동작
- **원칙:** 추측 금지. 공식 문서/이슈 트래커 확인 또는 `codex:rescue` 호출

### 일반 로직 버그
- 상태 관리, API, 네비게이션, 비동기 처리
- 아래 Phase 1 체크리스트 진행

## Phase 1: 근본 원인 조사

증상만 보고 바로 수정하지 않는다. 근본 원인을 먼저 특정한다.

**조사 체크리스트 (프레임워크별로 확장):**
- 상태 관리: 옵저버/리액티브 연결이 끊겼는가?
- 비동기: finally 블록에서 로딩 상태가 해제되는가?
- 네비게이션: pop/back이 비동기 완료 전에 호출되는가?
- API: 에러 응답을 성공으로 처리하는가?
- 이벤트: 리스너가 해제되지 않아 중복 실행되는가?

**조사 산출물 형식:**
```
[버그 증상] {사용자가 본 증상}
[근본 원인] {특정된 메커니즘 1~3줄}
[수정 대상] {파일명:라인번호}
[변경 내용] {old_string → new_string}
```

## Phase 2: 수정 — 위임이 기본

escape-hatch 조건을 확인한다. 해당하면 메인이 직접 수정, 아니면 dev 에이전트에 위임.

**위임 프롬프트 형식:**
```
[버그 증상]: {증상}
[근본 원인]: {Phase 1 조사 결과}
[수정 대상 파일]: {경로:라인}
[변경 내용]:
  old: |
    {정확한 코드 스니펫}
  new: |
    {수정된 코드 스니펫}
[범위 제한]: 위 변경만 수행, 추가 리팩토링 금지
```

## Phase 3: 검증

수정 후:
1. `{정적 분석 명령}` 실행 (Flutter: `fvm flutter analyze`, Python: `flake8`, JS: `tsc --noEmit`)
2. 에러/경고 확인
3. 원래 증상이 재현되지 않는지 확인 방법 사용자에게 안내

## Phase 4: QA 에이전트 검토 (3파일 이상 수정 시)

광범위한 버그 수정은 qa 에이전트로 패턴 일관성 검토.
