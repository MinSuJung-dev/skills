# DDD

DDD를 가르치는 스킬이 아니라, 코드보다 도메인 이해를 먼저 하게 만드는 개발 프로토콜이다. 산출물은 `docs/domain/`에 남아 세션이 바뀌어도 이어진다.

참고 파일은 **해당 Phase에 들어갈 때만** 읽는다.

| 파일 | Phase |
|------|-------|
| [STORY-FORMAT.md](STORY-FORMAT.md) — 스토리 문법, 템플릿, 검증 | 1 |
| [CANVAS.md](CANVAS.md) — 용어집, 이벤트, 컨텍스트 맵, 캔버스, 애그리거트, 유스케이스 | 2, 4, 5 |
| [HEURISTICS.md](HEURISTICS.md) — 경계 단서, 안티패턴 신호 | 3, 8 |
| [ARCHITECTURE.md](ARCHITECTURE.md) — 계층, 로직 위치, 모놀리스/MSA, 브라운필드, 테스트 | 5, 7 |
| [REVIEW.md](REVIEW.md) — 애그리거트 경계 질문, 설계 검증 게이트, DDD 리뷰 체크 | 5, 6, 8 |

## 원칙

- **DDD는 복잡한 비즈니스 규칙이 있는 곳에만.** 단순 CRUD·generic 영역은 단순한 구조가 우선이다. 판단이 서면 "이 기능은 CRUD로 충분" 이라고 말하고 Phase 7로 간다.
- **순서 강제.** 스토리 → 용어·규칙 → 경계 → 모델 → 검증 → 코드. 코드부터 만들지 않는다.
- **모르는 규칙은 추측하지 않는다.** 코드 → 테스트 → 문서 → 사용자에게 질문 → 그래도 없으면 `가정:`으로 명시.
- **기존 시스템은 점진적으로.** 근거 없이 구조를 갈아엎지 않는다 (ARCHITECTURE.md 브라운필드 규칙).
- **사람이 확인한 것만 확정.** 스토리는 다시 읽어 주고 확인받아야 `validated`. 동의어는 합치지 않고 충돌로 묻는다. 대화에서 나온 규칙은 즉시 파일에 적는다.

## 판단 우선순위 (규칙이 충돌할 때)

1. 기존 비즈니스 규칙 → 2. 기존 아키텍처 제약 → 3. 도메인 불변식 → 4. 바운디드 컨텍스트 경계 → 5. 프로젝트 코딩 컨벤션 → 6. 프레임워크 선호

## 금지

- 문서·코드에 없는 비즈니스 규칙 추론
- DB 테이블·연관관계로 애그리거트 만들기 (ERD → Entity → Service 흐름)
- 바운디드 컨텍스트 = 마이크로서비스로 간주, 근거 없는 MSA·메시지 브로커 도입
- 엔티티 행동으로 충분한데 도메인 서비스 만들기 / 인프라 일을 엔티티에 넣기
- 도메인 계층에 프레임워크·DB·HTTP·메시징 의존 (기존 컨벤션이 다르면 따르고 보고)
- 모든 상태 변경을 이벤트로 만들기
- 모든 영역에 애그리거트·리포지토리·이벤트 일괄 적용
- 도메인 이해 전에 아키텍처 최적화, 근거 없이 전체 재작성

## 산출물 (내용이 생길 때만 만든다)

```
docs/domain/
  stories/NNN-slug.md   # 스토리 + 주석 + 규칙/예시 + 이벤트 후보 + 미해결 질문
  glossary.md           # 용어(한국어) | 코드명(영어) | 정의 | 쓰지 말 것 | 컨텍스트
  context-map.md        # 서브도메인 분류 + 컨텍스트 관계 (컨텍스트 2개 이상일 때)
  contexts/<name>.md    # 캔버스 + 애그리거트 + 유스케이스
  reviews/NNN-slug.md   # 설계 검증 / DDD 리뷰 결과
docs/adr/NNNN-slug.md   # 되돌리기 어려운 경계·아키텍처 결정만
```

## 모드

요청에서 고른다. 불분명하면 `discover`부터.

| 모드 | Phase | 비고 |
|------|-------|------|
| `discover` | 0 → 1 → 2 | 도메인 전문가 인터뷰 / 레거시에서 as-is 추정 |
| `design` | 0 → 3 → 4 → 5 → 6 | Phase 6 통과가 끝 |
| `implement` | 0 → 7 | 해당 범위의 Phase 6 통과 기록 필요. CRUD 판정이면 불필요 |
| `review` | 0 → 8 | **새 서브에이전트나 `codex:rescue`에서 실행** — 작성자가 자기 코드를 검증하지 않는다 |

## Phase

- **0 조회** — `glossary.md`·`context-map.md`만 먼저 읽는다. 스토리·컨텍스트는 `grep -l`이나 front matter로 골라 연다.
- **1 발견** — 신규: 최근의 구체적 사례 하나를 요청, "그다음엔?"으로 이어간다. 레거시: 코드에서 as-is 스토리를 추정해 `draft (inferred)`. 질문은 하나씩, 추천 답 한 줄.
- **2 용어·규칙·이벤트** — 용어집 갱신, 주석·대화에서 규칙 → 예시 추출, 의미 있는 이벤트 후보만 기록. 모두 사용자 확인.
- **3 경계** — 경계 단서로 서브도메인 후보 제안 (근거 명시). 최종 경계와 core/supporting/generic은 사용자가 결정.
- **4 정의** — 컨텍스트 맵, Bounded Context Canvas. 연동 방식은 사용자 확인. 컨텍스트 1개면 건너뛴다.
- **5 전술 설계** — 일관성 경계 질문으로 애그리거트 결정, 엔티티/값 객체 구분, 로직 위치 결정, 유스케이스 작성.
- **6 설계 검증** — REVIEW.md 게이트를 채워 `reviews/`에 저장. 미통과 항목이 있으면 코드 금지, 사용자에게 보고.
- **7 구현** — 도메인 규칙 테스트(Given-When-Then)를 먼저 쓰고 구현. 이름은 용어집 코드명, 명령은 도메인 동사.
- **8 리뷰** — REVIEW.md 체크로 용어 어긋남·DDD 위반을 `file:line`과 함께 보고. 수정은 승인 후. 배선 누락은 `integration-audit`의 몫.

## 토큰 절약

- 넓은 코드 탐색은 Explore 서브에이전트에 맡기고 결론(`file:line` + 요약)만 받는다. 직접 볼 땐 `grep`부터.
- 산출물은 Edit로 부분 수정. 채팅엔 산출물을 복사하지 않고 요약 + 경로만.
- 이미 파일에 있는 내용은 다시 묻지 않는다. `contexts/<name>.md`가 200줄을 넘으면 애그리거트별로 분리.
