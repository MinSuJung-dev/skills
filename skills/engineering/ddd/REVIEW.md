# 설계 검증과 DDD 리뷰

## Phase 6 — 설계 검증 게이트

`docs/domain/reviews/NNN-<scope>-design.md`에 저장한다. 범위는 `DDD` 판정 컨텍스트 하나 (유스케이스가 많으면 유스케이스 묶음).

항목 결과: `통과` · `통과 (조건부)` · `미통과` · `해당 없음`. `해당 없음`과 `조건부`는 이유를 적는다.
- `미통과`가 하나라도 있으면 구현하지 않고 사용자에게 보고한다.
- `통과 (조건부)`: 진행은 하되 조건을 보고한다. 예: 용어·규칙이 `추천 수락`/`시뮬레이션`이라 사용자 재확인이 남음.

```markdown
---
scope: <컨텍스트 / 유스케이스>
date: YYYY-MM-DD
result: 통과 | 통과 (조건부) | 미통과
---

| 항목 | 결과 | 근거 |
|------|------|------|
| DDD 적용 여부 — 복잡한 규칙이 있는가, CRUD로 충분한가 | | |
| 도메인 경계 — 이 기능이 속한 컨텍스트가 정해졌는가 | | |
| 용어 — 필요한 용어가 모두 glossary.md에 확정됐는가 | | |
| 규칙 — 모든 규칙에 출처(스토리/코드/테스트/사용자)가 있는가, 가정은 표시됐는가 | | |
| 불변식 — 애그리거트마다 지키는 불변식이 적혀 있는가 | | |
| 애그리거트 경계 — 연관관계가 아니라 일관성 경계로 정했는가 | | |
| 엔티티 / 값 객체 구분 | | |
| 로직 위치 — ARCHITECTURE.md 결정 순서를 따랐는가 | | |
| 외부 의존 — 도메인이 포트로만 외부에 닿는가 | | |
| 트랜잭션 경계 — 유스케이스당 애그리거트 하나인가, 아니면 이유가 있는가 | | |
| 이벤트 — 각 이벤트에 반응하는 쪽이 있는가, Domain/Integration 구분 | | |
| 컨텍스트 간 의존 — 방향과 패턴이 context-map.md와 일치하는가 | | |
| 배포 구조 — 모듈형 모놀리스인가, MSA면 ADR 근거가 있는가 | | |
| 브라운필드 — API 계약·마이그레이션·기존 테스트 영향 확인 (해당 시) | | |
```

## 애그리거트 경계 질문 (설계 중·검증 시)

같은 애그리거트에 넣으려는 객체마다:
1. 반드시 **같은 비즈니스 규칙** 안에서 함께 변경되어야 하는가?
2. **같은 트랜잭션**에서 일관성이 즉시 보장되어야 하는가?
3. 외부에서 **독립적으로 변경**될 수 있는가? (그렇다면 분리하고 ID로 참조)

1·2가 아니오거나 3이 예면 분리한다. "관련 있다"는 이유만으로 넣지 않는다.

## Phase 8 — DDD 리뷰

새 서브에이전트나 `codex:rescue`에서 실행한다. **코드는 수정하지 않는다.** Phase 6 게이트는 설계 문서를 검증했을 뿐이다 — 구현이 설계를 어기는지는 여기서 본다.

**입력** (프롬프트에 명시해서 넘긴다)
- 범위: 기본은 커밋 범위의 diff. "전체"라고 하면 트리 전체.
- 필수 읽기: 이 파일, HEURISTICS.md, ARCHITECTURE.md, `glossary.md`, `context-map.md`, 범위에 해당하는 `contexts/*`와 스토리, `docs/adr/`.
- 이전 `reviews/*-design.md`는 근거이자 감사 대상이다 (체크 10).

**실행**
- 테스트를 돌린다.
- 금액·기간·상태 전이·재실행 같은 경계 시나리오는 프로젝트 파일을 건드리지 않는 탐침 스크립트로 직접 확인한다. 정적 읽기만으로 끝내지 않는다.

**판단 기준**
- 도메인 계층은 프로젝트 관례(패키지 또는 `domain` 파일명)로 판단한다. 모듈 공개 파사드·OHS 조회 모듈은 Application 계층으로 본다.
- 문서에 `범위 밖`·미해결 질문으로 적힌 것은 위반으로 보고하지 않는다 (보고서에 "제외" 한 줄).
- 출처 표기가 `가정`·`시뮬레이션`·`추천 수락`인 규칙은 위반이 아니다 → "사용자 확인 필요" 목록으로.

체크 (발견마다 `file:line` + 근거. 누락 테스트는 그 규칙을 구현한 코드의 `file:line`):
1. **용어** — 클래스·메서드·이벤트 이름이 glossary.md 코드명과 다르거나, `쓰지 말 것`에 있는 말을 쓰거나, 용어집에 없는 도메인 개념이 있다.
2. **출처 없는 규칙** — 스토리·테스트·문서 어디에도 없는 비즈니스 조건(기간, 금액, 상태 제한, 경계값 `>`/`>=` 등).
3. **계층 위반** — 도메인에서 프레임워크·ORM·HTTP·메시징 import. 엔티티의 저장/전송/알림 호출.
4. **로직 위치** — 애플리케이션 서비스의 비즈니스 `if`, getter/setter뿐인 엔티티, CRUD 모양 서비스(`create/update/delete/find`), 한 줄짜리 도메인 서비스.
5. **애그리거트** — 다른 애그리거트를 객체로 참조, ADR 없이 한 트랜잭션에서 여러 애그리거트 변경, ADR이 약속한 트랜잭션이 코드에 없음, 재실행·중복 실행으로 불변식 우회, 테이블 구조를 그대로 옮긴 모델.
6. **이벤트** — 구독자 없는 이벤트, 사소한 필드 변경 이벤트, 내부 모델을 그대로 노출하는 Integration Event.
7. **컨텍스트 경계** — 다른 모듈 내부 클래스(값 객체 포함)·테이블 직접 접근, context-map.md에 없는 의존.
8. **테스트** — 확정된 규칙에 대응하는 Domain Rule 테스트가 없다. 경계값·재실행 시나리오 테스트가 없다.
9. **과잉 설계** — `CRUD`·`CRUD + 검증` 판정 영역에 애그리거트·이벤트·포트, 근거 없는 MSA·브로커. (이 영역엔 캔버스·게이트 파일이 없는 게 정상이다.)
10. **문서·게이트 결함** — 설계 문서끼리 어긋남 (예: contexts와 context-map), 게이트가 통과시킨 항목이 코드에서 위반됨. 원인이 문서면 문서 위치를 적는다.

**심각도**
- `high`: 돈·데이터가 사라지거나 중복됨, 불변식 우회, 보안
- `medium`: 컨텍스트 경계·계층·트랜잭션 위반, 금지 용어, 게이트 결함
- `low`: 문서화 누락, 테스트 누락, 경미한 이름 문제

## 리뷰 보고 형식

`docs/domain/reviews/NNN-<scope>-review.md`에 저장하고 채팅에는 요약만.

```
DDD Review — <scope> (@ <commit>)
위반 N (high N / medium N / low N) · 테스트: N passed

체크별 결과
| # | 체크 | 발견 / 해당 없음 | 근거 한 줄 |

HIGH
1. src/order/domain/order.py:42 — 애그리거트
   근거: 같은 달 정산을 다시 실행하면 지급된 정산서를 덮어씀 (탐침 스크립트로 재현)
   제안: 이미 있으면 만들지 않는다

사용자 확인 필요 (가정·시뮬레이션·추천 수락, 또는 새로 드러난 규칙)
- src/order/domain/order.py:58 — 만료 시각 정각을 만료로 볼지

제외 (문서상 범위 밖)
- 소장권 취소 — contexts/access.md Open Questions

"fix 1" 또는 "fix all high"로 승인.
```

수정 후에는 보고서 끝에 `조치` 표(# | 수정/문서화/미결)를 덧붙인다.
