# 아키텍처와 구현 규칙

## 계층

| 계층 | 책임 | 하지 않는 것 |
|------|------|-------------|
| Domain | 비즈니스 규칙, 불변식, 상태 전이 | DB·HTTP·메시징·프레임워크 호출, 트랜잭션 관리 |
| Application | 유스케이스 조율: 로드 → 도메인 호출 → 저장 → 이벤트 발행, 트랜잭션 경계, 권한 | 비즈니스 규칙 판단 |
| Infrastructure | DB, 외부 API, 메시징, 이메일 등 어댑터 | 비즈니스 규칙 |

의존 방향: `Infrastructure → Application → Domain`. 도메인이 외부가 필요하면 **도메인(또는 애플리케이션)에 포트(인터페이스)를 두고 인프라가 구현**한다.

```
나쁨: Order 엔티티가 PaymentClient를 주입받아 직접 호출
좋음: Order.pay(paymentResult)  ←  PayOrderUseCase가 PaymentPort로 결과를 받아 전달
                                    PaymentPort  ←  PgPaymentAdapter (Infrastructure)
```

전술 빌딩 블록:
- **애그리거트**: 불변식을 지키는 가장 작은 일관성 경계. 다른 애그리거트는 ID로만 참조. 트랜잭션 하나에 하나, 경계 밖은 이벤트로 결과적 일관성.
- **엔티티**: 식별자로 구분되고 상태가 변한다. **값 객체**: 불변, 값으로 비교, 생성 시 검증 (금액, 이메일 등). 애매하면 값 객체부터.
- **리포지토리**: 애그리거트 루트당 하나, 인터페이스는 도메인 계층, 구현은 인프라.

기존 프로젝트가 도메인 클래스에 ORM 애노테이션 등을 이미 쓰고 있으면 그 컨벤션을 따른다 (판단 우선순위 2). 위반으로 보고만 하고 바꾸지 않는다.

## 로직 위치 결정 (Service를 만들기 전에 위에서부터)

1. **엔티티/값 객체** — 한 객체의 상태만으로 판단되는가? → 그 객체의 메서드
2. **애그리거트 루트** — 애그리거트 내부 여러 객체에 걸친 불변식인가? → 루트의 메서드
3. **도메인 서비스** — 여러 애그리거트에 걸친 *비즈니스 규칙*이고 어느 한 객체에 두면 어색한가? → 상태 없는 도메인 서비스 (드물어야 한다)
4. **애플리케이션 서비스** — 로드·저장·트랜잭션·외부 호출 순서를 조율할 뿐인가? → 유스케이스
5. **인프라** — 저장, 전송, 외부 형식 변환인가? → 어댑터

신호: 애플리케이션 서비스에 `if`로 비즈니스 규칙이 있다 → 1–3으로 내린다. 엔티티에 `send`, `save`, `notify`가 있다 → 4–5로 올린다.

`OrderService { create; update; delete; find }` 형태를 만들지 않는다. 유스케이스는 도메인 동사 단위 (`PlaceOrder`, `CancelOrder`).

## DB가 먼저 있을 때 (레거시)

테이블 = 엔티티로 옮기지 않는다. 테이블마다 묻는다:
- 비즈니스에서 이것은 무엇인가? 누가 언제 바꾸는가? (→ 스토리로 확인)
- 독립적으로 바뀌는가, 다른 것과 함께 바뀌어야 하는가? (→ 애그리거트 경계)
- 식별자가 의미 있는가, 값으로만 의미 있는가? (→ 엔티티 vs 값 객체)

영속성 모델과 도메인 모델이 달라도 된다. 매핑은 인프라 계층에서.

## 모놀리스 우선

기본값은 **모듈형 모놀리스**: 컨텍스트 = 모듈(패키지), 모듈 간 호출은 공개 인터페이스로만, 다른 모듈 내부·테이블 직접 접근 금지.

마이크로서비스는 아래 중 하나가 **확인됐을 때만** 제안하고 ADR로 남긴다:
독립 확장 필요 · 독립 배포 필요 · 팀 소유 경계 · 격리 요구(보안·장애) · 운영 제약.
메시지 브로커, 쿠버네티스, 서비스 메시, API 게이트웨이도 같은 기준.

## 브라운필드 규칙

- 먼저 분석하고, 변경은 한 경계·한 유스케이스씩.
- 변경 전 확인: 기존 API 계약(요청/응답 형태), DB 마이그레이션 영향, 기존 테스트.
- 기존 테스트는 유지한다. 깨지면 그 이유를 보고한다.
- 구조 개선은 기능 변경과 섞지 않는다. 필요하면 별도 제안으로.
- 스킬 범위 밖 파일 수정은 사용자 승인 후.

## 이벤트

- 다른 컨텍스트나 중요한 비즈니스 흐름이 **반응해야 할 때만** 만든다. `NameChanged`, `OrderViewed` 같은 것은 만들지 않는다.
- 이름은 과거형 도메인 용어 (`주문 확정됨` → `OrderConfirmed`).
- **Domain Event**: 컨텍스트 내부, 도메인 모델이 발생. **Integration Event**: 컨텍스트 밖으로 발행하는 계약 — 버전 관리하고 내부 모델을 노출하지 않는다.

## 테스트 수준

| 수준 | 대상 | 형태 |
|------|------|------|
| Domain Rule | 애그리거트·값 객체의 불변식 | Given-When-Then, 인프라 없이 |
| Application Use Case | 유스케이스 흐름 | 포트는 fake로 |
| Integration | 어댑터 ↔ 실제 DB·외부 시스템 | 필요한 경로만 |
| Contract | 컨텍스트/서비스 간 API·Integration Event | 공개 계약이 있을 때만 |

도메인 규칙 테스트는 스토리의 `규칙과 예시`에서 그대로 옮긴다:

```
Given 주문이 배송 중 상태일 때
When 주문 취소를 요청하면
Then 취소할 수 없다
```
