# 경계 단서와 안티패턴

## 경계 단서 (서브도메인 후보)

coarse 스토리에서 아래가 보이는 곳에 그룹 경계를 그어 본다. 단서는 후보일 뿐, 결정은 사용자가 한다.

| 단서 | 예 |
|------|---|
| 트리거가 다르다 | 고객 요청으로 시작 vs 매일 정해진 시각에 시작 |
| 용어가 바뀐다 | 앞에선 "주문", 뒤에선 "출고 건" |
| 같은 업무객체를 다르게 쓴다 | 주문서를 영업은 매출로, 창고는 피킹 목록으로 |
| 행위자 간 업무가 넘어간다 | 상담원 → 창고 담당자 |
| 스토리에 보이지 않는 무언가를 지원하는 활동 | 정산, 리포팅 |
| 변경 이유·속도가 다르다 | 요금 정책은 자주, 배송 흐름은 드물게 바뀜 |

## 분류

- **core**: 경쟁력의 원천. 직접 만들고 전술 패턴을 제대로 쓴다.
- **supporting**: 필요하지만 차별점은 아님. 단순하게 만든다.
- **generic**: 누구에게나 같은 문제 (인증, 결제). 구매·외부 서비스·CRUD로 충분.

## 안티패턴 신호 (Phase 8 리뷰, 설계 중 자가 점검)

| 안티패턴 | 신호 |
|---------|------|
| 빈약한 도메인 모델 | 엔티티는 getter/setter뿐, 규칙은 전부 `*Service`에 |
| 너무 큰 애그리거트 | "관련 있어서" 사용자·상품·결제·배송을 한 애그리거트에, 잦은 동시 수정 충돌 |
| 테이블 중심 모델 | `orders`/`order_items`/`payments` → `OrderEntity`/`OrderItemEntity`/`PaymentEntity` 1:1 |
| 만능 엔티티 | 엔티티에 `sendEmail`, `notify`, `save` 같은 인프라 일 |
| 이벤트 남발 | `NameChanged`, `OrderViewed`, 구독자 없는 이벤트 |
| 전사 단일 모델 | 모든 컨텍스트가 같은 `User`/`Order` 클래스를 공유 |
| CRUD 모양 서비스 | `OrderService { create; update; delete; find }`, `cancelOrder` 같은 도메인 동사가 없음 |
| 불필요한 도메인 서비스 | 엔티티 메서드 하나로 충분한 로직을 `*DomainService`로 분리 |
| 도메인의 프레임워크 의존 | 도메인 패키지에서 ORM·DI·HTTP·메시징 import |
| 기술 용어 이름 | `OrderManager`, `DataProcessor`, `InfoHelper` |
| ACL 누락 | 외부 API 응답 모델이 도메인 계층까지 그대로 들어옴 |
| 컨텍스트 = 마이크로서비스 | 경계마다 배포 단위를 기계적으로 분리 |
| 패턴 과잉 | generic/CRUD 영역에도 애그리거트·이벤트·리포지토리 일괄 적용 |
