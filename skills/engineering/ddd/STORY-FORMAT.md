# 도메인 스토리 형식

## 문법

한 문장 = 한 활동.

```
N. 행위자 –활동→ 업무객체 [→ (to/with) 행위자]
```

- **행위자**: 능동적으로 일하는 사람·그룹·시스템. 스토리 안에서 **같은 이름은 한 행위자**.
- **업무객체**: 다루는 것 (문서, 물건, 디지털 정보). 도메인 용어로 이름 붙인다. 활동마다 다시 적는다.
- **활동**: 동사. 행위자·업무객체는 명사, 활동은 동사.
- **번호**: 발생 순서. 같은 번호 = 동시에 일어남.

## 범위 (front matter에 기록)

| 축 | 값 |
|---|---|
| granularity | `coarse` (전체 흐름) / `fine` (세부 단계) |
| time | `as-is` (현재) / `to-be` (미래) |
| purity | `pure` (소프트웨어 없음) / `digitalized` (시스템도 행위자) |

시작은 coarse · as-is · pure. 요구사항에 가장 가까운 건 fine · to-be · digitalized.

## 금지와 대처

- **if/else, 반복 금지.** 가장 흔한 경우 하나를 구체적 사례로 말한다.
- 작은 변형·선택 단계 → **주석**.
- 중요한 대안 → **별도 스토리** (`NNN-slug-alt-...`).
- "가끔은…"이 반복되면 → 새 스토리가 필요하다는 신호.
- 전문가 의견이 갈리면 → 하나를 가정으로 골라 주석에 적고 진행, 미해결 질문에 올린다.
- 가상의 사례("~할 수도 있다")와 실제 사례를 섞지 않는다.

## 템플릿 — `docs/domain/stories/NNN-slug.md`

```markdown
---
id: 001
title: 고객이 주문을 한다
granularity: coarse
time: as-is
purity: pure
status: draft | draft (inferred) | validated
storyteller: <누가 말했나 / 추정 근거 파일>
updated: YYYY-MM-DD
---

## 스토리
1. 고객 –전화로 요청한다→ 주문 → 상담원
2. 상담원 –작성한다→ 주문서
3. 상담원 –전달한다→ 주문서 → 창고 담당자

## 그룹 (경계 후보)
- 주문 접수: 1–2
- 출고: 3–

## 주석
- (2) 단골 고객은 주문서 대신 메모로 받기도 함

## 규칙과 예시
- 규칙: 재고가 없으면 주문을 받지 않는다
  - 예시: 재고 0개인 상품 A 주문 → 거절, 고객에게 입고 예정일 안내
  - 출처: 사용자 확인 (YYYY-MM-DD) | 코드 file:line | 테스트 | 가정

## 이벤트 후보
- 주문 확정됨 (3) — 반응하는 쪽: 창고 (출고 준비)

## 미해결 질문
- [ ] 주문 취소는 누가 할 수 있나?
```

## 검증 체크리스트 (validated 전)

- [ ] 모든 문장이 `번호. 행위자 –동사→ 업무객체` 형태인가
- [ ] 조건 분기·반복이 없는가
- [ ] 번호가 순서대로인가
- [ ] 모든 행위자·업무객체가 `glossary.md`에 있거나 추가 후보로 올렸는가
- [ ] 규칙마다 출처가 있고, 추측한 규칙이 없는가
- [ ] 이벤트 후보마다 반응하는 쪽이 있는가
- [ ] 스토리 전체를 사용자에게 다시 읽어 주고 확인받았는가

## 스토리 → 사용자 스토리 (fine · to-be · digitalized에서만)

사람 행위자가 시스템 행위자와 주고받는 활동 하나 = 사용자 스토리 후보 하나.
`<행위자>로서 <업무객체>를 <활동>하고 싶다`. 후보로만 제시하고 확정은 사용자가 한다.
